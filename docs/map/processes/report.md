# report

Turning a session's verified samples into a number a lab can act on, and a file it can hand
over.

**Input** — a session id and a signed-in medtech.
**Output** — a persisted [`Report`](../objects/Report.md) row and a CSV file in
`Documents/AgarthaVision/`.

**consumes** [`Session`](../objects/Session.md), [`Sample`](../objects/Sample.md),
[`Detection`](../objects/Detection.md), [`Finding`](../objects/Finding.md)
**produces** [`Report`](../objects/Report.md)

## Movement

1. **Require cached identity and ownership.** `GenerateSessionReportUseCase` fails if there is
   no cached local identity (i.e. the device has never signed in), if the session is missing,
   or if the session is not owned by the current user
   (`domain/usecase/records/GenerateSessionReportUseCase.kt:42-50`). Works offline when signed
   in; blocked when the device has never signed in (no cached identity).
2. **Gather.** Fetch the session's non-flagged samples and each one's detections
   (`domain/usecase/records/GenerateSessionReportUseCase.kt:48-51`).
3. **Count.** `getConfirmedEggCountsForSession` groups by `COALESCE(expert_class, class_label)`,
   joins to samples, and excludes flagged samples, and false positives
   (`data/local/dao/DetectionDao.kt:33-52`).
4. **Fetch Findings.** Fetch the per-species egg counts logged by the medtech for each field
   (`data/local/dao/SampleSpeciesFindingDao.kt:getFindingsForSession`).
5. **Compute LPF Range.** Philippine medtechs use Direct Smear, so density is reported per 
   Low Power Field (LPF) as a min–max range per species, not a mean
   (`domain/usecase/reports/LpfAggregation.kt`, `domain/model/LpfDensity.kt`).
   - **Range:** `min(eggCount) .. max(eggCount)` across all fields recorded in the session.
   - **Zero contributes, not absence:** a field containing none of that species contributes 0,
     so a species found in 3 of 10 fields reads `0–4`, not `1–4`.
   - **Denominator is whatever was recorded:** no minimum floor, no cap. Ten fields is typical
     practice, not an app-enforced rule.
   - **Semi-quantitative descriptor:** read off the *highest* single field (rare ≤2, few 3–5,
     moderate 6–10, numerous >10), not the mean. A single heavy field must not be averaged away
     by nine clean ones.
   - **Wholly negative session is valid:** `0–0` for every species produces a report normally.
6. **Normalise species** to canonical names, falling back to the raw label when unrecognised
   (`domain/usecase/records/GenerateSessionReportUseCase.kt`).
7. **Build the CSV** — a comment-prefixed header block (report id, session id and label,
   timestamps, patient id, device id, generated by, totals, positive species, per-species LPF range) 
   then one row per detection, or one row for a sample with no detections
   (`domain/usecase/records/ReportCsvBuilder.kt:14-34`).
8. **Write the file** to `Documents/AgarthaVision/` as
   `agarthavision-session-{sessionId}-{reportId}.csv`
   (`data/repository/DocumentsReportFileStore.kt:31-38`).
9. **Insert the row** with `supabase_status = pending`, then push it —
   row only, no file upload (`domain/usecase/records/GenerateSessionReportUseCase.kt`).

## Live LPF, without a report

`SessionEggCountUseCase` runs the same aggregation without writing anything. It is what 
Session Detail displays before anyone generates a report.

## Decision records

### 1. No WHO infectivity tier (PB-16, ticket 86d4be3wz)

The app previously shipped an infectivity tier derived from Kato-Katz EPG thresholds
(`InfectivityLevelCalculator.kt:21-25`). It was deliberately deleted:
- WHO's light / moderate / heavy classification is defined strictly for eggs-per-gram (EPG)
  measured by Kato-Katz. There is no WHO or DOH intensity table for direct fecal smear.
- Philippine medtechs use **Direct Smear**, so the app has no EPG figure to classify.
- The thresholds that were in `InfectivityLevelCalculator.kt` (Ascaris 5,000/50,000; Trichuris
  1,000/10,000; Hookworm 2,000/4,000) are EPG-scale. They cannot be rescaled to an LPF count,
  and replacing them would mean inventing a threshold table that does not exist in the literature.
- Ticket 86d4a6jxw reached the same conclusion independently: *"Do NOT claim a WHO light/moderate/heavy
  class off an LPF count. If an infectivity tier is wanted on the report, it needs its own clinical sign-off."*
- What ships instead is the conventional wet-mount semi-quantitative descriptor — rare / few /
  moderate / numerous — read per organism at 10× objective (`domain/model/LpfDensity.kt:LpfDescriptor`).
- **Reopening condition:** a tier may return **only** with a cutoff table clinically signed off for
  direct-smear LPF, by name and date. Not by analogy to Kato-Katz, and not by rescaling.

### 2. What "LPF range" means (PB-17, ticket 86d4be3zb)

Three definitions were in circulation: a mean, a highest-single-field, and the min–max range.
The figure is pinned in `domain/usecase/reports/LpfAggregation.kt:aggregateLpfPerSpecies`:
- **Per species:** `min(eggCount) .. max(eggCount)` across all fields recorded in the session.
- **A field with none of that species contributes 0, not absence.** If Ascaris is seen in 3 of 10
  fields with counts 1, 4, and 2, the range is `0–4`, not `1–4`. Dropping empty fields would
  systematically overstate every result. Zero-egg fields persist as data because 86d4a6prb persists
  zero-detection inference frames; if empty frames are ever discarded or filtered, every range in
  the app silently corrupts.
- **The denominator is whatever the medtech recorded** — no floor, no cap. Ten fields is typical
  practice, not an app-enforced rule.
- **The descriptor comes from the highest field, not the mean:** rare ≤2, few 3–5, moderate 6–10,
  numerous >10. A single heavy field must not be averaged away by nine clean ones.
- **A wholly negative session is a real result:** `0–0` for every species, and a report still
  generates (rendering "no parasites found" rather than failing or showing an empty state).

## Hits

- **The counting rule.** Any change to the WHERE clause in
  `data/local/dao/DetectionDao.kt:33-52` or how findings are stored in `sample_species_findings`
  silently changes LPF everywhere.
- **The CSV column set**, which is a downstream consumer contract even though nothing in this
  repo parses it.
- Report generation is idempotent in the sense that it always creates a *new* row; it never
  updates an existing one.

## Does not hit

- **Existing reports or their files.** Regenerating writes a new row and a new file under a new
  report id. Old CSVs stay on disk under their old names, and stale files are never cleaned up.
- **Storage.** The CSV never reaches Supabase — only the row does. `csv_file_path` is a
  device-local path that no other client can resolve.
- **Sample or detection state.** Reporting is read-only over both. Generating a report does not
  mark anything as reported.
